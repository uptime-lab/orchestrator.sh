Network boot Over HTTP, from any network

No PXE. No boot server on site.

Network boot usually means a DHCP server you control and a TFTP server next to the boards. Here the board's own bootloader fetches a signed recovery system over HTTP from your server's name. The server can sit in another building, in another country or in our cloud.

Network

Any network with DHCP

The board needs an Ethernet cable and an ordinary address. Nothing changes on the router.

Transport

Plain HTTP, port 80

The board trusts the signature, not the connection. An image signed by another key does not boot.

Drive

Empty is fine

Recovery runs from RAM. The drive can be blank, broken or about to be erased.

Setup

Once per board

The bootloader learns the server's name and key from the browser over USB, from a provisioning card, or from a board that already runs Linux.

T+0 to T+6 Minutes, from recorded runs

Blank to managed in about six minutes

Over the internet, a CM5 Lite went from approval to a managed Ubuntu in 5 min 42 s and a CM4 in 6 min 9 s.

  1. T+0

    Approved

    You approve the board by its hardware serial.

  2. T+0

    Bootloader flashed

    The board now boots from the server first.

  3. T+2

    Recovery booted

    A 98 MB recovery system, signed with the server's key, runs from RAM.

  4. T+3

    OS written

    The image streams onto the drive. Ubuntu took 81 seconds on a CM4.

  5. T+4

    Agent installed

    The signed agent goes in with the board's own credential.

  6. T+6

    Online

    The board boots from its own drive and reports in.

Run it on a fresh Ubuntu or Debian machine, x86-64 or arm64. The same command covers both setups below: the installer asks which one you want.

On your local network

For a lab, an office or a home rack. The server answers over plain HTTP by the name your router gave the machine. No domain and no certificate needed.

From the internet

For boards in other places. Point a DNS name at the machine and the installer gets and renews a Let's Encrypt certificate.

  • The name must not change: every board you adopt stores it.
  • Network boot is one more yes. It creates your signing key and signs the recovery image.
  • By hand with your own reverse proxy, follow the install guide.

What you do with it next

    

      
Users and keys
Set Linux users, SSH keys and sudo for one board, a unit or the whole account.

      
Images and backups
Capture a configured board as a golden image and install it on the next ten. Back up a drive and restore it later.

      
Terminal and recovery

Playbooks

Architecture What checks what

    
Every step checks the next one

    
Nothing runs on a board because it arrived over the network. Each stage carries the key that checks the stage after it.

    

      
Bootloader
Checks the recovery image
Every server creates its own signing key. The bootloader holds the public half and refuses an image that key did not sign.

      
Recovery image
Carries the agent
The agent is inside the signed image. Recovery downloads no code at all.

      
Agent
Checks the OS image
It writes the image you picked and makes the drive bootable only when the SHA-256 matches the one sent over TLS.

      
Agent
Checks every package
Agent packages are signed on hardware keys kept offline. The server checks them on import and the board checks again before installing.

    

    
This is not full Secure Boot: the bootloader key can be rewritten by someone holding the board, and the installed OS boots unsigned. How the chain works and where it stops.
